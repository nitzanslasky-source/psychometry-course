# Topic 42 Formal logic and deductions

######## SECTION vr42-learn — Learn and try (learn)
=== VIDEO vr-logic-condition-result: kind=lesson title='Deductions: condition → result'
[1] Treat the rule as a promise
  BOARD: ['Every blue badge is magnetic.', 'Blue badge → magnetic']
  SCRIPT: Every blue badge is magnetic. Think of that as a promise about anything that meets the condition: if it is a blue badge, it must be magnetic. Blue badge goes on the left of the arrow, and magnetic goes on the right. These are the condition and the result. The arrow does not have to describe a cause or a sequence in time. Being a blue badge need not cause magnetism. It simply tells us which combination the rule allows. For this question, accept the rule as given even if an invented world behaves differently from the real one.
[2] Condition present: result required
  BOARD: ['Blue badge ✓ → magnetic ✓']
  SCRIPT: If I show you a blue badge, the condition has been met. The promised result must follow: the badge is magnetic. We are not guessing from how most badges behave. We are applying a rule that says every blue badge. This first case is the straightforward direction of the arrow. When a longer problem gives several rules, look for a fact that starts one of the arrows. That fact lets you move forward. If the new result starts another arrow, you may be able to continue. We will build those chains in a moment, but every valid chain begins with this same small step.
[3] Condition absent: the rule is silent
  BOARD: ['Not a blue badge → undetermined', 'A red badge may still be magnetic.']
  SCRIPT: Now I show you something that is not a blue badge. Does it have to be nonmagnetic? No. The rule made a promise about blue badges, and we have stepped outside that condition. A red badge might be magnetic too. The result is undetermined, which means the information allows more than one possibility. It does not mean the object has no definite properties in reality; it means this rule does not tell us which properties it has. This is one of the two common traps. Denying the condition does not let us deny the result. We should be able to imagine a non-blue magnetic badge without breaking the original rule.
[4] Result present: the condition is not guaranteed
  BOARD: ['Magnetic → undetermined', 'Many different objects could be magnetic.']
  SCRIPT: Suppose we are told only that an object is magnetic. Must it be a blue badge? Again, no. The original promise did not say that blue badges are the only magnetic objects. A result can be shared by several conditions. A helpful everyday comparison is: every square has four sides, but not every four-sided shape is a square. In the invented badge world, a magnetic red badge is a perfectly good counterexample to the reverse claim. We use such a counterexample to show that a conclusion does not have to follow. We are not claiming the counterexample actually exists unless the question says it does.
[5] Result absent: the condition is impossible
  BOARD: ['Not magnetic → not a blue badge', 'Otherwise the promise would be broken.']
  SCRIPT: Finally, an object is not magnetic. Could it be a blue badge? It cannot, because a blue badge must be magnetic. If we labeled this nonmagnetic object a blue badge, we would break the rule. This is the valid backward move: reverse the arrow and negate both sides. In plain English, if the promised result is missing, the condition cannot have been met. Do not remember this as merely ‘reverse the rule.’ Reversing without changing both sides gives the invalid case we just rejected. The meaning is the safest memory aid: a blue badge with no magnetism is the one forbidden combination.
[6] The four cases together
  BOARD: ['Condition yes → result yes', 'Condition no → no conclusion', 'Result yes → no conclusion', 'Result no → condition no']
  SCRIPT: Here are the four cases in one place. Condition present: result required. Condition absent: no conclusion about the result. Result present: no conclusion about the condition. Result absent: condition ruled out. Instead of memorizing four unrelated lines, keep the promise in mind. The rule forbids condition yes with result no. Every other combination can occur. This gives us a second method: draw four small boxes for the two yes-or-no properties and cross out only that forbidden box. The two methods agree. Use arrows for quick chains and the boxes when you need to check whether a proposed counterexample is actually allowed.
[7] Only points to a requirement
  BOARD: ['Only trained staff may enter.', 'May enter → trained', 'Trained does not guarantee permission.']
  SCRIPT: Only trained staff may enter. Ask: if someone may enter, what must be true of them? They must be trained. That puts permission to enter on the left and trained on the right. The phrase immediately following ‘only’ names the required group here. It is not automatically the condition on the left. A trained person might still lack a pass, so training alone does not guarantee permission. Rephrase the whole sentence as an if-then promise before drawing an arrow. This is especially useful with ‘only if’: the gate opens only if the code is correct means gate opens, therefore code correct. It does not by itself say every correct code opens the gate.
[8] No and none exclude an overlap
  BOARD: ['No silver tokens are square.', 'Silver → not square', 'Square → not silver']
  SCRIPT: No silver tokens are square. Draw two circles that cannot overlap, or write silver implies not square. The valid reverse-and-negate version is square implies not silver. Notice that this does not say all tokens are silver or square. A round bronze token fits the rule perfectly well. The rule excludes one shared region; it does not describe the whole universe. Now consider ‘There is no blue badge that is not magnetic.’ The forbidden thing is a blue badge without magnetism, so this is another way of saying every blue badge is magnetic. Remove the double negative by identifying the combination being forbidden, not by crossing out every word ‘not’ you see.
[9] If and only if gives two arrows
  BOARD: ['Access if and only if approved', 'Access → approved', 'Approved → access']
  SCRIPT: If and only if is a stronger statement than a one-way rule. It says each condition is enough for the other. If a file is accessible if and only if it has been approved, access implies approval and approval implies access. We can move in either direction because both directions were supplied. The same idea appears in wording such as ‘all approved files, and only those files, are accessible.’ Keep the word ‘only’: without it, we would have only one arrow. When a question asks whether a feature lets us decide a second feature completely, this two-way relationship is often what is needed.
[10] Chain at the matching middle
  BOARD: ['Courier → registered', 'Registered → carries a pass', 'Courier → carries a pass']
  SCRIPT: All couriers are registered, and all registered people carry a pass. Registered is the result of the first rule and the condition of the second, so the arrows join. A courier must carry a pass. Compare that with courier implies registered and gardener implies registered. Those two arrows end at the same place. They do not tell us that couriers are gardeners. A shared result is not a bridge. Before linking two rules, check that you are leaving one arrow exactly where the next arrow starts. If a negative version would create the match, write the valid reverse-and-negate form first, then connect it.
[11] Some gives you a real witness
  BOARD: ['Some musicians are cyclists.', 'All cyclists wear helmets.', 'Some musicians wear helmets.']
  SCRIPT: The word ‘some’ tells us that at least one example exists. Take that example with you through a rule. Some musicians are cyclists, and every cyclist wears a helmet. The musician who is a cyclist must therefore wear a helmet. We may conclude that some musicians wear helmets. We cannot conclude that all musicians do. Nor can we combine ‘some musicians are cyclists’ with ‘some cyclists are painters’ and assume it is the same cyclist. The two ‘some’ statements may refer to different people. Give the first witness a small dot or an imaginary name, then track that same witness rather than silently replacing it.
[12] A universal rule does not supply an example
  BOARD: ['All moon gardeners wear purple.', 'This alone does not establish a moon gardener.']
  SCRIPT: A rule about all members of a group does not, by itself, tell us that the group has any members. ‘All moon gardeners wear purple’ may be a perfectly consistent rule even if there are no moon gardeners. This matters when an answer begins with ‘some.’ To establish that someone exists, look for a stated example or a statement such as ‘there are’ or ‘some.’ The ordinary fact that real humans exist should not quietly fill that gap in a made-up logic question. We are checking what follows from the information supplied. Once an example is supplied, use it confidently, but keep its properties attached to that one example.
[13] Disprove a rule with one forbidden case
  BOARD: ['Rule: all amber stones are smooth.', 'Counterexample: amber AND not smooth.']
  SCRIPT: To contradict ‘all amber stones are smooth,’ we need one amber stone that is not smooth. A smooth stone of another color is irrelevant. An amber smooth stone follows the rule rather than contradicting it. This is the same forbidden combination from our four cases: condition present and result absent. If a question asks for one object that disproves two claims, write the forbidden combination for each claim and combine them. Check that your chosen object violates both, not merely one. A very short table with one row per claim can prevent a long, tangled sentence from taking over the problem.
[14] Distinguish certainty from possibility
  BOARD: ['Must be true: every allowed case', 'Could be true: at least one allowed case', 'Cannot be true: no allowed case']
  SCRIPT: Before testing an answer, read the question’s demand carefully. A ‘must’ answer survives every allowed arrangement. A ‘could’ answer needs just one allowed example. A ‘cannot’ answer fails in every allowed example. These are different jobs. For a must question, one valid counterexample is enough to reject an option. For a could question, one working example is enough to accept it. We will use this habit again in rules and arrangements. Your active-reading note can be as small as circling MUST or CANNOT. That one mark is often more valuable than underlining every noun in the premises.

=== VIDEO solve-vr42-g001: kind=solution title='The four cases in a new setting'
[1] Your question
  BOARD: []
  SCRIPT: All sealed parcels are labeled. Which of the following must be true?
[2] Write the promises
  BOARD: ['Sealed → labeled', 'Not labeled → not sealed']
  SCRIPT: A sealed parcel without a label would break the rule. Therefore, an unlabelled parcel cannot be sealed. The rule permits labeled unsealed parcels and supplies no example of a sealed parcel. Read each arrow as an if-then promise. Keep every negative word attached to the property it changes. For an “only” statement, ask which property is required; for a statement beginning with “some,” keep track of the example whose existence is actually supplied.
[3] Try to break the proposed inference

Every unsealed parcel is unlabelled.: Unsealed parcels fall outside the condition and may still have labels. There is at least one sealed parcel.: A universal rule does not guarantee a member of its condition group. The useful test is whether an alternative can fail while all the given statements remain true. If it can, it is not guaranteed.
